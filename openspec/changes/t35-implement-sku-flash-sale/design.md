## Context

See `proposal.md` for motivation and scope. The agreed UX is in `../../../docs/ui-ux/t35-implement-sku-flash-sale.md`.

The repository already has `MarketplaceCampaign`, product-level `SellerCampaignProduct.discountBasisPoints`, `ProductPromotionReservation` for promotion overlap, and `ScheduledDiscountService` shared by catalog/quotes. That promotion reservation is a schedule guard, not physical stock or a buyer hold. `CheckoutService.confirmCod` already uses a serializable transaction, idempotency, inventory reserve/consume, and voucher consumption. Buyer cancellation and seller rejection already restore inventory through order lifecycle services. Extend these paths instead of adding a second checkout or stock ledger.

The campaign foundation and the completed CMS separation change are dependencies. Some campaign task checkboxes predate current code; implementation must verify actual endpoints and behavior rather than reimplement from checkbox state. There is no durable Flash Sale quota or product-level buyer claim yet.

## Goals / Non-Goals

**Goals:** separate FE/BE delivery against one shared contract; make quota, stock, one-time claims, and COD reversals transactionally consistent; preserve the explicit sold-out state until replenishment or end.

**Non-Goals:** production CDN/private-ingress topology, strict FIFO waiting order, multi-instance acceptance, production capacity claims, JWT key rotation, payment waiting reservations for Flash Sale, Redis outage/cache-loss restoration, disaster reconciliation, production/cloud deployment, multi-region/Redis Cluster distribution, advertising, ML/data pipelines, and changes to post-delivery returns. Normal command rollback and idempotency remain in scope. Buyer sold-progress displays from original T35 are removed by user decision. Do not claim the original T35 cache recovery criteria are satisfied.

## Decisions

### 1. One modular monolith and two workstreams

Use NestJS/TypeScript + Prisma/PostgreSQL, a local standalone Redis with versioned Lua scripts and the repository-compatible Redis client, existing worker conventions, and Next.js/React. BE owns contracts in `packages/contracts`, schema, services, scripts, and API/integration tests. FE owns Seller/Buyer surfaces and their tests. `tasks.md` has exactly BE and FE sections, with dependencies marked.

Keep campaign scheduling/admin placement in the existing domain. Add a Flash Sale boundary consumed by pricing, inventory, checkout, cancellation, and campaign commands; pricing owns final price composition, inventory owns physical quantities. Keep business modules together; the ingress SQS/Lambda control plane in section 10 is a separate admission boundary, not a separate order/inventory service. PostgreSQL-only would omit T35's Redis allocation direction; Redis-only would lose durable authority.

### 2. SKU identity, money, quota, and claims

Proposed additive records (names finalized in implementation without changing semantics):

| Record | Fields and constraints |
| --- | --- |
| `FlashSaleSku` | id, campaignId, sellerParticipationId, productId, variantId, referencePriceMinor, salePriceMinor, allocatedQuantity, remainingQuantity, netConsumedQuantity, version, managementEpoch, endedAt, endedReason; unique campaignId/variantId |
| `FlashSaleBuyerClaim` | campaignId, buyerId, productId, variantId, purchaseId, orderLineId, createdAt; unique campaignId/buyerId/productId; retained after cancellation |
| `FlashSaleConsumption` | orderLineId unique, flashSaleSkuId, quantity=1, sale-price snapshot, reversedAt, reversalDestination (`FLASH_SALE` or `NORMAL`); one reversal per consumption |
| Flash Sale command/audit | actor, scope, UUID key, canonical request digest, response, source/target version and quota delta; use existing command/audit infrastructure where compatible |
| Projection outbox | eventId, per-SKU sequence/version, managementEpoch, operation token, admission delta, absolute public state, attempt status; same transaction as the business write |

Money uses existing integer minor units. Registration captures a fixed per-SKU sale price and reference price, validates the campaign minimum discount (current Flash Sale default 10%), and counts the existing 20-products-per-seller policy by distinct products, not SKU rows. Before enrollment closes, existing edit policy can update prices; after it closes prices are fixed. Quantity-only edits remain allowed until startsAt. Reference-price mutation on an enrolled SKU must not rewrite an advertised discount; reject incompatible base-price edits until participation ends.

Define `availablePhysical = quantityOnHand - quantityReserved` using existing inventory semantics. `remainingQuantity` is the unsold sale allocation; `allocatedQuantity` is cumulative supplied allocation, adjustable before opening and incremented by sold-out replenishment; `netConsumedQuantity` counts non-reversed sale units. Track normal-returned units in reversal records rather than assuming allocated=remaining+netConsumed after end. Canceled orders do not mean paid orders, and COD creation does not mark payment paid.

Protect backing using `availablePhysical >= sum(remaining protected allocations)` for each SKU. Registration/replenishment do not reduce physical stock. Ordinary new reservations, adjustments, and online reacquisition must subtract protected remaining allocations when checking availability; a sale confirmation excludes its own allocation from that ordinary guard while atomically reducing both stock and quota. Existing online holds are already excluded from availablePhysical and cannot be reassigned to Flash Sale.

This implementation uses conservative backing: even future accepted allocations are included until canceled/ended; no unproven reuse of the same physical units across future allocations. Preserve existing promotion overlap rules. Do not extend a product-percentage discount onto nonparticipating siblings.

### 3. Derived lifecycle with explicit termination

Persist termination and quantities, derive state using campaign publication/cancellation and fresh database time:

| State | Condition | Seller operations / buyer result |
| --- | --- | --- |
| `UPCOMING` | Eligible registered SKU, now < startsAt | Edit quota within backing; ordinary price and unprotected ordinary availability |
| `ACTIVE` | startsAt <= now < endsAt, not ended, remaining > 0 | No quota/price edits; sale price, sale badge, quantity=1, COD |
| `SOLD_OUT` | Same active interval, not ended, remaining=0 | Replenish or end SKU; no SKU sale badge, unavailable, no ordinary purchase |
| `ENDED` | Seller ended, campaign canceled, or now >= endsAt | Ordinary current price/available stock; no reopening in same campaign |

Initial quota must be positive. Pre-start edit replaces quota with a positive integer; removing registration uses existing withdrawal rules, not an implicit zero edit. At sold-out, replenishment takes `additionalQuantity > 0`, requires available physical backing, and preserves price/claim identity. Termination targets one SKU, requires zero quota during the active interval, and does not end siblings. Campaign end releases remaining backing logically; an optional worker can persist bookkeeping, but correctness cannot wait for a scheduler. Old Redis expiry or index state never extends the sale window.

### 4. Peak-phase admission before the database — critical

Separate public read snapshots from quota-admission state. The read path is L1 in-memory cache -> L2 Redis -> controlled PostgreSQL fill. After backend validation of the Redis-backed traffic token (section 10), the COD write path is authentication/rate limit -> advisory L1 precheck -> Redis atomic admission -> PostgreSQL transaction. A positive L1 cache hit never bypasses Redis, and a stale L1 negative cannot permanently deny replenished quota: refresh through Redis at the bounded freshness threshold. Never decrement quota or maintain the authoritative buyer limit in per-instance memory.

Use one short, versioned Lua admission call for all sale lines on standalone Redis. Keys include campaign+SKU counters, campaign+buyer+product claims, operation+attempt tokens, and a shared configured concurrency budget. Pass all keys explicitly and validate all lines before any writes; runtime script errors are not transactional rollback. [Redis scripting semantics](https://redis.io/docs/latest/develop/programmability/eval-intro/)

1. Validate auth/origin and request shape using existing authentication. Apply per-buyer and shared rate limits and a finite in-flight checkout budget; if full, return 429/Retry-After without allocating quota or waiting in an unbounded queue. Existing auth or bounded idempotency reads are allowed; the guarantee is avoiding allocation locks and checkout transactions for rejected traffic, not zero SQL for every request.
2. Resolve idempotency before a new allocation: cached committed operation results replay; an in-progress same-key attempt returns processing/retry guidance. On uncertain or missing operation state, perform a bounded durable purchase lookup under the existing command identity before granting again. Never turn an already successful retry into sold-out merely because current quota is zero. Rate-limit repeated lookups.
3. Redis checks campaign time/management epoch, remaining admission quota, and product-level buyer claim; it atomically obtains a concurrency slot and provisional token and reduces admission availability only if every line is eligible. Reject before PostgreSQL allocation locks on insufficient quota, used claim, end, or saturation. Token contains server-derived SKU/product/campaign identities, quantities, request digest, attempt id and management epoch. It is not a buyer-visible reservation and is never trusted from client fields.
4. Only admitted requests enter the existing bounded serializable PostgreSQL transaction. Reuse command/cart locks, compatible campaign locks, product-claim advisory locks, allocation rows, and inventory locks in deterministic order across all affected paths. After waits, evaluate clock_timestamp(), recheck token identity/management epoch and the DB quota/stock/claims/price/vouchers, then write purchase, claims, consumption, quota, stock and outbox together. Existing reserve+consume is internal to this COD transaction. [PostgreSQL locking](https://www.postgresql.org/docs/current/explicit-locking.html)
5. Normal database retries reuse the admission token without another quota decrement; a definitively aborted attempt releases exactly its own token before a new attempt can obtain another. Before success, the final locked time check must fall in the active window; Redis admission before endsAt alone does not preserve eligibility while waiting. A DB transaction accepted at its final check may commit just after endsAt.
6. After commit finalize the token without subtracting its sale quota a second time, retain the buyer claim, release the concurrency slot, and cache replay result. On proven rollback, compare-and-release only that token's quota and temporary claim and slot. On ambiguous commit, resolve the durable purchase first; timeout or token TTL must never automatically return a possibly committed unit. A token deadline prevents late admission/commit but is not permission to release uncertain stock. Unresolved operations conservatively retain capacity; automatic orphan/crash recovery remains deferred.

Maintain two distinct Redis representations: public snapshots (absolute state+version) and admission counters/tokens (provisional availability). Public cache fills never initialize or overwrite live admission counters. Initialize admission only during controlled first publication/registration; missing live admission state returns unavailable, rather than seeding from an uncoordinated DB read.

Routine outbox events carry event id, affected SKU sequence, management epoch, operation token, admission delta, and absolute public snapshot. Apply admission events exactly once in contiguous per-SKU sequence (buffer/retry gaps); sale finalization contributes zero additional admission decrement, replenishment/restoration adds only its committed delta, termination closes admission, and ordinary rollback release is token-scoped. Never assign DB remaining directly over counters that include concurrent provisional admissions. Public snapshots accept only newer versions; publish L1 invalidation only after the matching L2 snapshot is installed. These normal command events are in scope, not a disaster rebuild.

Seller replenishment/end and admin cancellation update the durable state and management epoch under their normal locks. Until the corresponding admission event is applied, old-epoch tokens may reach PostgreSQL but fail its epoch check and compensate safely; after end, old token release cannot reopen admission. Replenishment and new claims wait for the committed management update to reach Redis. Seller sold-out actions continue to use DB remaining, not provisional admission exhaustion; if admission capacity is temporarily exhausted while durable quota remains, return busy/retry rather than claiming that the seller may end it.

Redis and PostgreSQL do not share a transaction. DB guarded updates and unique constraints remain final authority despite stale admission. This protocol deliberately moves ordinary losers ahead of PostgreSQL locks, while keeping accepted checkout synchronous and bounded. No background order-execution queue or promise of purchase after quota admission is introduced; section 10 adds a user waiting queue before business ingress.

### 5. Cancellation and replenishment races — critical

Extend the shared cancellation/rejection transaction rather than adding a separate restock endpoint. Lock the original sale participation and consumption using the same order as seller commands. Existing inventory restoration runs once; the Flash Sale hook must not increment physical stock again. For an unreversed consumption, restore quota only if the original participation has no endedAt, campaign is not canceled, and fresh locked time is inside the original interval. `SOLD_OUT` still qualifies. Otherwise set reversal destination NORMAL and leave quota closed. Mark reversed, update net consumption and public-state version, and emit outbox events in that transaction. Keep the buyer claim for all successful-order cancellation actors in this version; failed creation never created one.

If cancellation wins first, quota becomes positive and a stale sold-out end/replenish command conflicts. If termination wins first, cancellation returns ordinary stock only. Cancellation after a replenishment adds the canceled unit to remaining quota; it also restores its corresponding physical unit, so backing remains valid. Restock never targets a later campaign on the same variant. Existing cancellation eligibility remains authoritative; shipped/delivered return flows are not extended by this change.

### 6. One price and availability contract — critical

Extend the central pricing boundary with a discriminated variant result: `NORMAL`, `FLASH_SALE_ACTIVE`, `FLASH_SALE_SOLD_OUT`, with campaign/participation identity, evaluatedAt, endsAt, stateVersion, priceSource, effectivePriceMinor, canPurchase, allowedPaymentMethods and buyer reason when authenticated. Seller/private contracts additionally expose quota/warehouse fields. Public sale contracts omit warehouse surplus and exact quota; rendering alone is not sufficient to hide it.

For a SOLD_OUT SKU return canPurchase=false and no purchasable sale offer; if a price is required by the existing contract, use a reference/display price explicitly marked unavailable. Do not fall through to a normal scheduled discount. Ended participation exits to the normal resolver; keep the underlying ordinary price, subject to independently valid ordinary promotions. Representative card prices and badges are derived from purchasable variants. Do not grant a Flash Sale campaign boost to ordinary siblings just because their parent product had participation. Hydration uses the bounded public snapshot path in section 9 for cached/indexed results; checkout rechecks authoritative state. Explicit price sort is preserved.

Keep existing bounded search ordering rather than implementing a new ranking engine. Common card, detail, cart, quote and homepage consumers must consume the same sale metadata. Use the L1/L2 hierarchy, original snapshot age limit, and both start/end boundaries in section 9; emit versioned invalidation on quota or end changes. Do not cache buyer claims in a shared public response. FE refreshes with the phase-specific polling, focus and countdown rules in section 9; no new websocket system is required.

Voucher thresholds use the effective merchandise prices after the SKU discount, then existing voucher stacking/rounding rules. A mixed selection with any sale line is COD-only for the entire purchase. Reject online intent creation and retries when newly evaluated sale lines would be purchased; an older normal-price online order with an already-valid hold remains governed by its immutable snapshot. A stale quote requires a new preview; never silently substitute price, quantity, SKU, or payment method.

### 9. Three traffic phases and the L1/L2 read hierarchy

L1 is a bounded LRU cache inside each NestJS instance; L2 is shared Redis. Cache only public SKU/product data with canonical keys including campaign/SKU and representation version. Keep buyer claims, personalized quotes and seller data outside shared public responses. Bound request batches, key cardinality and cache memory. Full-page refreshes and SSR must reuse this public cache for sale/card hydration instead of reading each sale SKU from PostgreSQL again; unrelated authenticated page work may still use DB.

Start with L1 TTL 0.5–1 second and a hard public-snapshot age limit of 2 seconds measured from the original authoritative read. Copying L2 into L1 must preserve that original age, never restart it. Outbox snapshots retain their commit/evaluation timestamp; delayed delivery must not renew old data. An expired unchanged version can be revalidated by a fresh guarded DB read, without allowing an older version to overwrite a newer one. Cap validity at both startsAt and endsAt and evaluate time transitions on the server. Timed state identity includes the derived phase as well as the mutation version. Outbox updates install newer L2 snapshots then publish invalidation to every L1 instance through internal Redis Pub/Sub; missed invalidations are bounded by the original age limit. This accounts for [Redis Pub/Sub at-most-once delivery](https://redis.io/docs/latest/develop/pubsub/#delivery-semantics). Version fences must prevent a concurrent older fill from reinstating invalidated data. No stale-while-revalidate across this hard bound or sale boundaries.

Public cache misses use per-process single-flight and a short distributed per-key fill lease, with bounded wait and bounded DB fill concurrency. Only the fill owner reads PostgreSQL; other requests reuse the result or receive a retryable response instead of all falling through to DB. Expiry jitter cannot extend hard validity. This read-cache mechanism never reconstructs live admission counters. Prewarm campaign metadata and controlled initial admission state at publication, and prewarm public metadata shortly before startsAt; admission itself checks server time so it cannot open early. L1 warms on demand on each instance.

| Phase | FE behavior | BE behavior |
| --- | --- | --- |
| 1: Before opening | Use server-time offset for local countdown; visible-page status refresh every randomized 10–15 seconds; one refresh within 0–500 ms after startsAt, then use phase 2 cadence | Prewarm; serve repeated/full-page reads through L1/L2; boundary-aware cache expiry and coalesced fills prevent a database stampede |
| 2: Active peak | Refresh visible sale states at randomized 3–5-second intervals; disable duplicate submission; obey Retry-After and retain the same idempotency key for an unchanged checkout retry | L1/L2 absorb reads; per-buyer/shared rate limits and Redis atomic admission enforce a finite global checkout budget before PostgreSQL allocation transactions |
| 3: Sold out but ongoing | Show sold out without SKU sale badge; keep randomized 3–5-second foreground checks so replenishment or cancellation restoration becomes visible | Cache SOLD_OUT; committed replenishment/reversal updates versioned public snapshots and admission deltas; explicit end restores ordinary selling |

Use one request in flight per poller, deduplicate visible SKU ids, pause while hidden, refresh on return with jitter, back off on errors/429, and stop sale polling once participation/campaign ends. Never auto-submit an order when quota reappears. No browser WebSocket/SSE system is required. Redis Pub/Sub here is internal cache invalidation only.

Add a public lightweight batched status endpoint: GET /campaigns/:campaignId/flash-sale/status?variantIds=... (1–50 unique ids from that campaign). Return serverTime, startsAt, endsAt and per-SKU lifecycle state, stateVersion, public price and canPurchase; canPurchase is generic eligibility, not a guarantee or buyer-specific claim result. Return no exact quota or private stock. Generate serverTime at response assembly rather than caching an old clock value. Polling must not refetch the whole catalog or cart quote.

Under normal operation, backend public snapshots are at most 2 seconds old; a visible healthy page should reflect a committed replenishment/end/reversal within an 8-second acceptance target (2 seconds snapshot age + at most 5 seconds until next poll + 1 second request/render budget). Measure this target; hidden tabs, network failures and overload backoff are excluded. Checkout always uses authoritative validation even inside this display window. Seller command responses show their committed result immediately.

Validate all three phases on the single API instance used by the POC: cold/warm cache, simultaneous full-page refresh, boundary transitions, stale L1 after replenishment, missed invalidation, out-of-order public fills, sold-out polling, 429 behavior, and peak COD contention. Record L1/L2 hit rates, DB public-fill counts, PostgreSQL checkout transaction count, admitted/rejected counts, in-flight peak, latency and visibility delay. Normal quota/limit/overload losers must not enter allocation transactions; no throughput capacity is claimed before measurement.

### 10. LocalStack waiting room and Redis admission pool (approved POC revision)

Topology: Browser -> static Waiting Room UI (CDN/edge role, served locally for the POC) -> Admission/Queue API backed by Lambda and SQS Standard in LocalStack -> Redis admission state. The browser polls the control plane to receive its token, then calls the business Backend directly with that token. The backend validates admission before invoking protected checkout logic. Queue messages are admission tickets, not background order-execution jobs. One NestJS API, PostgreSQL and standalone Redis are sufficient for acceptance; production CDN, private origin, proxy admission gateway, HA and multi-instance deployment are outside scope.

Use SQS Standard as explicitly selected, not FIFO: delivery may repeat or arrive out of order. Never promise exact position or strict arrival order. Join uses an authenticated buyer/gate identity plus its own Idempotency-Key and request digest; retries and multiple tabs reuse one live ticket. Different request content with a reused key conflicts. Lambda handling is idempotent by ticket ID, independently of SQS message ID. Queue delivery must not duplicate a grant or an order. Order confirmation retains its separate existing Idempotency-Key and digest.

Redis holds tickets, buyer/session bindings, opaque random admission tokens, expiry metadata and shared capacity. The pool contains 20 lease slots, not 20 pre-generated reusable credentials. An atomic grant checks that the ticket is still waiting and that capacity exists, binds a fresh cryptographically random token to buyer/session/gate/ticket, and records a 300-second lease from grant time. Token state is stored in Redis with that TTL. No JWT signing/issuer/key rotation is used. Repeated grant delivery returns the recorded outcome without extending the deadline. A token must be recoverable through authorized status polling during its original lease if the first response is lost.

When all 20 lease slots are occupied, the buyer remains WAITING and no token is issued. Keep the ticket pending for later SQS/Lambda processing; do not acknowledge and lose an ungranted ticket. SQS visibility/redelivery must use a bounded backoff rather than a busy loop; the interval is local implementation tuning, not a buyer-facing promise of entry. Acknowledge a granted message only after its grant is recorded; expired/closed or duplicate messages must not issue a new lease. Join publication failures must be retryable under the same ticket/key, not create orphaned successful joins. Polling reads state and never itself grants capacity or queries checkout/order/PostgreSQL. Retain bounded waiting-ticket lifetime/queue size and server-directed 5–10-second jittered polling from the existing UX; these are tuning values, not a grant-rate target.

Only carts containing server-classified Flash Sale lines, including mixed carts, require admission when protection is enabled. Determine applicability from authenticated selected cart lines and authoritative sale metadata, never a client-provided flag. Minimal cart/eligibility reads for classification are permitted; a waiting buyer does not repeatedly request preview. Ordinary-only carts bypass this gate. Flash Sale preview validates the token but uses no confirmation slot. Existing COD-only validation continues to reject online payment for sale lines; online routes are not an alternative admission path.

Every protected request validates the opaque token against live Redis state and authenticated buyer/session, gate/scope and server deadline. No positive validation cache bypasses this check. Deliver the token in a same-origin HttpOnly SameSite cookie, Secure when using HTTPS; configure local transport explicitly without exposing the token in URLs/localStorage or requiring manual copying. Status responses are private and no-store. Missing/expired tokens return 428 admission guidance; invalid or mismatched tokens return 403; unverified Redis state returns 503, with no per-process quota/token fallback. This is failure behavior, not Redis disaster recovery.

There are exactly two traffic capacities: at most 20 active buyer leases and at most 5 simultaneous Flash Sale order-confirmation executions. The latter is a Redis atomic budget acquired before quota allocation/creation processing, not a requests-per-second rate and not a limit on preview. Integrate the quota admission path with this five-confirmation ceiling rather than retaining an independent effective 100-slot ceiling. If all five are occupied, return 429/Retry-After without allocating quota; the buyer retains the lease and retries manually with the same order key. In-progress duplicate commands must not launch another execution. Existing committed-result lookup/replay is resolved without creating another order.

Release a lease exactly once on successful order creation, after its original 300-second deadline, or when the buyer relinquishes admitted access. An explicit leave releases immediately when no confirmation is executing. A last-tab close or navigation away sends a best-effort page-leave signal and schedules release after a 5–10-second grace period; a refreshed page or another live tab heartbeat cancels that pending release. Heartbeats never extend the original lease deadline, a hidden/background tab alone never releases a lease, and a missing page-leave signal falls back to the original deadline. Preview, definitive checkout failure, and sold-out/quote errors retain the lease so the buyer can continue or retry unless the buyer also leaves. If confirmation is executing, record the relinquish request but defer lease release until processing reaches a definite result; client disconnect never terminates downstream work.

Waiting cancellation and admitted relinquishment are distinct idempotent transitions. Both must validate the authenticated buyer/session, ticket and current lease identity, use compare-and-release accounting, and keep external ticket state ADMITTED while a grace release is pending. Refresh and same-session tabs reuse the live ticket and coordinate a browser-instance heartbeat so one tab cannot release access still used by another. After early release or expiry, a new admission cycle uses a new ticket/key, and delayed heartbeat, queue, page-leave or success events from an old cycle cannot recreate or revoke a newer lease. Expiry accounting must reclaim pool capacity from explicit deadline records atomically; token-key disappearance alone must not leak or double-return slots. When the periodic expiry reaper reclaims one or more leases, it immediately runs `grantWaiting`; SQS redelivery remains a retry fallback, not a liveness dependency. A successful commit releases by the lease ID captured for that command; delayed success cannot revoke a newer lease. No automatic lease renewal.

A confirmation slot is released only once processing finishes or termination is confirmed, regardless of success/failure. A lost connection or lease expiry does not mean downstream work stopped. Quota-attempt tokens remain internal to the COD transaction protocol in section 4; neither returning a lease nor expiring a traffic token restores product quota. Resolve uncertain commits before compensation. A buyer with a lost successful response can use authenticated result lookup by the original order key even after its lease was released. Seller replenishment adds product quota; it does not reset the admission pool, pending tickets, token deadlines or permanent purchase claims. Admission never reserves a SKU or guarantees a purchase. Campaign time/price rules still apply and the UI requests price review when the sale ends.

API inventory under /api/v1: control-plane POST /admission/checkout/tickets (join Idempotency-Key), GET /admission/checkout/status (owned ticket, WAITING/ADMITTED/EXPIRED/CLOSED and expiry; delivers cookie), DELETE /admission/checkout/ticket to cancel only an ungranted ticket, POST /admission/checkout/relinquish for an authenticated explicit or page-leave admitted-release request, and POST /admission/checkout/heartbeat for the live browser instance to cancel only its matching pending grace release. Relinquish and heartbeat require origin/CSRF protection, ticket/session/lease ownership and idempotent stale-event handling; neither renews the lease. Backend GET /admission/checkout/results/:idempotencyKey is authenticated existing-command lookup only. Test checkout preview and COD confirmation, ordinary-cart bypass, mixed-cart gating and existing online-sale rejection. Retain 401 authentication and 409 idempotency-content conflict conventions; never reinterpret admission overload as an invalid token.

## Risks / Trade-offs

- [Redis and DB cannot commit together] -> DB is final authority; attempt-scoped compensation and versioned normal event propagation; acknowledge unavailable admission after unresolved failures. Outage/cache-loss recovery is deferred, not silently implemented.
- [Hot SKU contention among admitted requests] -> pre-DB admission, bounded shared concurrency, short scripts, deterministic locks, finite retries, measured three-phase local POC contention tests. This first version prioritizes correctness over maximum throughput.
- [Double restock or lost sale backing] -> reuse inventory restoration once, protect ordinary reservation paths, and add one durable reversal marker per order line.
- [Sold-out mistaken for ended] -> separate explicit endedAt from derived quota state, and test cancellation/end/replenish races.
- [Legacy product discounts leak to siblings] -> route FLASH_SALE through SKU resolver, gate quota-less records, preserve other types and CMS separation.
- [No purchase-right restoration after cancellation] -> user-approved rule remains visible in checkout; apply consistently and test separately from quota restoration.

## Migration Plan

1. Add schema, constraints, indexes, local Redis runtime, and versioned contracts. No automatic production actions. Seed explicit upcoming, active, sold-out, ended, and sibling variants without changing existing order history.
2. Introduce `FLASH_SALE_SKU_ENABLED` default false. Inventory backing guards and reversal reads must be deployed before enabling writes; reuse existing homepage campaign flags for placement, not economic truth.
3. Inventory legacy Flash Sale registrations. Require explicit SKU/price/quota enrollment; retain legacy rows for audit but exclude them from the enabled SKU-price path. Reuse current campaign admin and seller participation ownership. Do not infer quota from all warehouse stock.

Read cache fills must never reset live admission counters. Refresh affected search projections and inspect authoritative hydration. Do not mark T35's deferred recovery criteria complete or edit GitHub automatically.
5. Rollback means disable new Flash Sale admission and registration while retaining durable order/claim/reversal records and inventory guards for unfinished participation. Keep sold-out gating until controlled termination/expiry; never fall back to legacy discounted checkout. Confirmed orders/cancellations remain supported. No destructive down-migration while references exist.
