## Context

T02 established the pnpm/Turborepo applications and repository gates, while T03 added Prisma migrations, deterministic seed data, and a guarded database verifier. The API currently runs on the host and requires `DATABASE_URL`; contributors must supply PostgreSQL themselves, and no GitHub Actions workflow exists. See `proposal.md` for the motivation and the two capability specs for observable requirements.

The design must work on Windows developer machines and GitHub-hosted Linux runners, preserve the pinned Node.js 22.12.x and pnpm 10.34.5 toolchain, avoid committed secrets, and never let smoke verification target normal development data.

## Goals / Non-Goals

**Goals:**

- Make PostgreSQL provisioning and daily lifecycle operations one-command, repeatable, and diagnosable.
- Reuse T03's migration, seed, constraint, and URL safety verification instead of creating a second persistence test path.
- Make clean-machine smoke verification cross-platform and isolated from long-lived developer state.
- Run equivalent repository and persistence gates on pull requests and direct pushes to `development` or `main`.
- Keep credentials ephemeral or explicitly local-only and redact them from script errors.

**Non-Goals:**

- Containerizing the Next.js or NestJS applications for daily development.
- Production images, deployment, secret management, backups, observability, or high availability.
- Redis or other infrastructure not required by current application behavior.
- Repository branch-protection administration; CI produces checks that protection rules can require separately.

## Decisions

### 1. Compose manages PostgreSQL only

`compose.yaml` will run a pinned PostgreSQL 18 image with a named development volume, a loopback-only configurable host port, and `pg_isready` health check. An initialization script will create the separate `_test` database on first volume initialization. Web and API processes remain host-run for fast reload and straightforward debugging.

This follows the accepted architecture and keeps Compose focused on infrastructure. Containerizing both applications was rejected because it adds image/watch complexity without helping the T04 acceptance criteria.

### 2. Environment templates are executable local examples, not secrets

A root `.env.example` will list Compose, API, development, and test variables with conspicuous local-only values. `.env` and all non-example variants remain ignored. Documentation will state that these values are unsafe for deployment and must never be reused outside an isolated workstation. Compose will require the variables it consumes instead of silently inventing production-like defaults.

Using a committed realistic password was rejected because it can be mistaken for a deployable credential. Omitting authentication through PostgreSQL trust mode was also rejected because it weakens even a loopback development setup.

### 3. Daily lifecycle uses simple root commands; smoke uses an orchestrator

Root package scripts will wrap Compose for `infra:up`, `infra:down`, `infra:status`, `infra:logs`, and explicitly destructive `infra:reset`. The normal commands use the contributor's ignored `.env` and stable Compose project resources.

The cross-platform clean-machine test will be a Node.js ESM script. It will choose free ports, generate runtime-only local credentials, set a unique Compose project name, start PostgreSQL with ephemeral storage, invoke the existing `db:verify`, launch the built API on a free port, assert the health response, and remove the exact project resources in a `finally` path. A programmatic orchestrator was chosen over chained package commands so cleanup and redaction remain reliable on both Windows and Linux.

### 4. One CI workflow has repository and persistence jobs

The workflow will trigger for pull requests to `main` and `development`, pushes to both branches, and manual dispatch. A repository job will install the exact pnpm version, restore pnpm caching, perform frozen installation, run Prisma format/validate/generate checks, then run format, lint, typecheck, tests, and build. A separate persistence job will run the isolated infrastructure smoke command, giving database failures a distinct result.

Splitting every command into a separate job was rejected because repeated dependency installation would add latency at this repository size. Combining persistence into the repository job was rejected because independent diagnostics and Docker cleanup are clearer when infrastructure verification is isolated.

### 5. CI uses least privilege and superseded-run cancellation

Workflow permissions default to `contents: read`. Concurrency keys will be based on workflow plus pull request or branch reference, with `cancel-in-progress: true`. Runtime test credentials are supplied only as job environment values or generated by the smoke process and are redacted before output.

Action dependencies will be pinned to reviewed immutable commit SHAs with their release tags documented in comments. Floating major tags were rejected because upstream tag movement changes CI behavior without a repository commit.

## Risks / Trade-offs

- **[The initialization script runs only for a new PostgreSQL volume]** → Document that configuration changes may require the explicit destructive reset command and make that data-loss boundary prominent.
- **[A fixed developer port can already be occupied]** → Make the host port configurable and include port inspection guidance; smoke verification selects free ports dynamically.
- **[Compose project cleanup could target contributor resources]** → Generate a unique project name, verify it before cleanup, and issue destructive Compose commands only with that exact name and file.
- **[Runtime credentials could appear in child-process diagnostics]** → Sanitize full URLs and user/password authority fragments before printing captured output.
- **[Two CI jobs duplicate dependency installation]** → Use pnpm caching; keep job separation for fault isolation until runtime data justifies further optimization.
- **[Direct pushes can still occur without branch protection]** → Run CI on those pushes and document the recommended required checks; repository policy configuration remains intentionally external.

## Migration Plan

1. Add templates, Compose assets, lifecycle commands, and the isolated smoke orchestrator without changing existing database migrations.
2. Validate Compose interpolation using the example environment and run the smoke workflow from an empty Docker state.
3. Add contributor documentation and update the T03 note that deferred infrastructure to T04.
4. Add the CI workflow, verify its syntax locally where possible, then push to `development` so the first real GitHub-hosted run exercises the complete workflow.
5. If local infrastructure must be rolled back, stop the T04 Compose project and remove the added workflow/scripts. Preserve the named volume unless the maintainer explicitly chooses the destructive reset.
