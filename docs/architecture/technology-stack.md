# Technology Stack and Engineering Conventions

Status: Accepted

Decision owner: Project maintainer

Tracking issue: [#2 — T01 Confirm architecture, stack, and engineering conventions](https://github.com/datnguyen101004/shopee_clone/issues/2)

## 1. Architecture baseline

The Shopee clone starts as a TypeScript modular monolith in a pnpm workspace. The frontend and backend are independently deployable applications, while framework-neutral contracts and tool configuration are shared through workspace packages.

This baseline optimizes for fast delivery, consistent types, simple local development, and clear module boundaries. It does not prevent extracting services later when measured scale or ownership needs justify the additional operational cost.

## 2. Approved technology stack

| Layer | Decision |
|---|---|
| Package manager | pnpm with a committed lockfile |
| Monorepo orchestration | pnpm workspaces and Turborepo |
| Frontend | Next.js App Router with React and TypeScript |
| Backend | NestJS with TypeScript and REST APIs |
| Database | PostgreSQL |
| ORM and migrations | Prisma |
| API documentation | OpenAPI generated by NestJS Swagger |
| Local infrastructure | Docker Compose |
| CI | GitHub Actions |
| Frontend unit tests | Vitest and Testing Library |
| Backend unit tests | Jest |
| Backend integration tests | Jest, Supertest, and an isolated PostgreSQL test database |
| Browser tests | Playwright |

Exact runtime and dependency versions are pinned when T02 scaffolds the applications. Supported versions must be active LTS or stable releases and must satisfy the chosen framework compatibility matrix.

## 3. Repository layout and ownership

```text
shopee_clone/
├── apps/
│   ├── web/                 # Next.js buyer, seller, and admin interfaces
│   └── api/                 # NestJS REST API and business modules
├── packages/
│   ├── contracts/           # Framework-neutral API types, enums, and generated clients
│   ├── config/              # Shared TypeScript, lint, and formatting configuration
│   └── ui/                  # Reusable frontend UI primitives when introduced
├── docs/                    # Architecture and contributor documentation
├── openspec/                # Product specifications and change artifacts
└── compose.yaml             # Local infrastructure definition
```

Boundaries:

- `apps/web` owns presentation, browser interaction, and client-side state. It never accesses PostgreSQL directly.
- `apps/api` owns business rules, authorization, persistence, transactions, and integration adapters.
- `packages/contracts` contains no NestJS, Next.js, Prisma, or database implementation code.
- `packages/ui` is frontend-only and cannot import backend modules.
- Prisma schema and migrations are owned by `apps/api` because the backend is the sole persistence boundary.
- Feature code is organized by business capability, such as catalog, identity, cart, checkout, order, seller, and admin—not by generic controller/service folders at repository root.

## 4. Backend conventions

The NestJS application is a modular monolith. Each business capability exposes an explicit module boundary and keeps transport, application, domain, and persistence concerns distinguishable without forcing unnecessary abstraction.

### REST API

- All public application endpoints use the `/api/v1` prefix.
- JSON property names use `camelCase`; URL paths use lowercase `kebab-case` nouns.
- Resource identifiers are opaque strings in API contracts.
- Collection endpoints use server-side pagination with a consistent metadata envelope.
- OpenAPI is generated from the backend and is the source for API documentation and generated clients.
- Breaking changes require a new API version or an explicit migration plan.

### Error format

Errors use `application/problem+json`, based on Problem Details, with stable machine-readable extensions:

```json
{
  "type": "https://shopee-clone.local/problems/validation-error",
  "title": "Request validation failed",
  "status": 400,
  "detail": "One or more fields are invalid.",
  "instance": "/api/v1/products",
  "code": "VALIDATION_ERROR",
  "traceId": "opaque-trace-id",
  "errors": [
    { "field": "price", "message": "must be greater than zero" }
  ]
}
```

Stack traces, SQL details, secrets, and internal exception messages are never returned to clients.

### Validation and data integrity

- Every external input is validated at the NestJS boundary with explicit DTOs and a global validation pipe.
- Unknown fields are rejected for write operations.
- The server recalculates prices, discounts, shipping, permissions, and stock; client-calculated values are never authoritative.
- Prisma and PostgreSQL constraints enforce uniqueness, required relationships, and transactional invariants.
- Date-times are stored and transported in UTC using ISO 8601; presentation converts them to the user timezone.
- Money is stored as integer minor units unless a later domain requirement documents a different decimal strategy.

## 5. Naming and code conventions

- TypeScript runs in strict mode; avoid `any` unless a documented boundary requires it.
- Classes, React components, types, and enums use `PascalCase`.
- Variables, functions, methods, and JSON properties use `camelCase`.
- Files and directories use `kebab-case`, following framework-required filenames where applicable.
- Environment variables use `UPPER_SNAKE_CASE`.
- Physical PostgreSQL names use `snake_case`; Prisma fields may remain `camelCase` with explicit mappings.
- Avoid cross-feature imports into internal implementation files. Import only a feature's public contract.
- Prefer small, explicit modules over premature generic frameworks.

Formatting and static analysis are automated. Generated code and migration files are not manually reformatted when that would break their generators.

## 6. Testing strategy

Testing follows the risk and boundary being changed:

- Unit tests cover business rules, calculations, validation helpers, and state machines.
- API integration tests cover controllers, authorization, Prisma queries, transactions, and error contracts against an isolated database.
- Frontend component tests cover important states and user interactions.
- Playwright covers critical buyer, seller, and admin journeys.
- Contract compatibility is checked through OpenAPI generation and client/type generation.
- Every defect fix adds a regression test at the lowest useful level.

CI runs install, format/lint checks, type checking, tests, and production builds. Later issues may add security, migration, and end-to-end gates.

## 7. Environment and configuration

- Supported environments are `development`, `test`, `staging`, and `production`.
- `.env.example` documents required variables using safe placeholders; real `.env` files and secrets are never committed.
- Applications validate environment variables at startup and fail fast with a useful, non-secret error.
- Docker Compose provides local PostgreSQL and future infrastructure dependencies; applications may run on the host for fast development.
- Configuration is injected from the environment. Production secrets are supplied by the deployment platform.
- Logs are structured and must not contain credentials, tokens, payment data, or unnecessary personal data.

## 8. Git and delivery conventions

- Commits follow Conventional Commits, for example `feat(cart): add cart item quantity update`.
- Work branches include the issue number and a short slug when practical.
- Pull requests reference their issue, summarize behavior changes, and list verification performed.
- Database schema changes include migrations and compatibility notes.
- A task closes only when its acceptance criteria and required checks pass.

## 9. Non-goals and deferred decisions

The initial architecture deliberately excludes:

- Spring Boot or a second backend implementation.
- Microservices, event sourcing, service mesh, and Kubernetes.
- GraphQL as a public application API.
- Native Android or iOS applications.
- Real payment capture, carrier contracts, and financial settlement before their roadmap phases.
- Redis until a feature such as concurrency-safe Flash Sale demonstrates the need.
- Machine-learning recommendations before sufficient behavioral data and evaluation criteria exist.
- Production-scale livestream transcoding and CDN infrastructure.

These are deferred, not forbidden. Adopting one requires an OpenSpec change documenting the problem, benefits, migration, and operational cost.

## 10. Decision consequences

Benefits:

- One primary language across frontend and backend reduces context switching.
- NestJS provides explicit modules, dependency injection, validation, OpenAPI integration, and a natural path to background jobs and realtime features.
- PostgreSQL and Prisma support transactional marketplace workflows and reproducible migrations.
- The modular monolith keeps deployment and debugging manageable while preserving capability boundaries.

Trade-offs:

- The team must actively prevent shared TypeScript packages from becoming tightly coupled implementation dumping grounds.
- Prisma-specific persistence details remain inside the API and are not shared with the frontend.
- Scaling the monolith requires observability and profiling before deciding whether to extract services.
